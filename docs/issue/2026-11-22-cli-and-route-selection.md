# 短い綴りを作る CLI と、手法を名指しして選ぶ口 (CLI と `_ex`)

## 概要

kawaz の案 (2026-11-22)。下の 4 つが元の案。ライブラリの `_ex` に手法を名指しする口を足さないことは「方向」の節、決まった事は DR-0018 にある。

- 短い綴りを作って出す CLI を作る。sockat を組み込めないプログラム (他人の作ったコマンド) に、長いパスの代わりに渡す
- CLI は引数で条件と手法を選べる。手法を指定して作れなければエラーにする
- 手法の名前を並べて、その順に試させる口も欲しい。API (`_ex` の引数の戦略の設定) に入れてもよく、そこでなら fork の手法を戻してもよい
- `/proc` を通る綴りも CLI で使える。利用者が開いたディレクトリの fd を渡すオプションを置き、`/proc/<持ち主の pid>/fd/<N>` を B として使う

## 分かっていること

### CLI が出した綴りの寿命

- `/proc/<pid>/fd/<fd>/…` の綴りは、その pid のプロセスが fd を持っている間だけ辿れる (SPEC の `until: Process`)。CLI 自身の pid と fd で作ると、CLI が終わった時に辿れなくなる
- 持ち主を呼ぶ側のプロセス (シェル等) にすれば成り立つ。別のプロセスが同じ uid で `/proc/<pid>/fd/<fd>/D/E/<名前>` に届くことは実測済み (DR-0017 の Context)
- 既定の B (`/tmp/sockat-<uid>`) の中に CLI が D を作ると、flock を持つプロセスがいなくなり、他の利用者の `sweep()` と OS の掃除で消されうる。利用者が持つディレクトリを B にすれば、これは起きない
- 使えるのは Linux で `/proc` を使え、同じ uid・同じ PID 名前空間の相手だけ

### 持ち主の pid を親の pid から決める時の罠 (実測 2026-11-22、macOS)

コマンド置換の中で起こしたプロセスから見た親の pid が、呼んだシェル本体か。

| 起こし方 | bash 3.2 | zsh | dash |
|---|---|---|---|
| `$(cmd)` | 本体 | 本体 | 本体 |
| `$(cmd \| cat)` | 別 (すぐ終わる) | 別 | 別 |
| `$(true; cmd)` | 別 | 本体 | 本体 |
| `$(env cmd)` | 本体 | 本体 | 本体 |

- 親の pid を黙って使うと、パイプや複文の中で、すぐ終わるプロセスを持ち主にしてしまう。`/proc/<pid>/fd/<N>` と渡された fd の `(st_dev, st_ino)` の照合は、その時点で同じディレクトリかしか見ないので、すぐ終わる親を見分けられない
- 持ち主の pid は、fd と組の引数で受ける (シェルなら `$$`。kawaz 2026-11-22)。pid と fd は片方だけでは意味が無い
  - 2 つのオプションに分けるなら、fd 無しで pid だけ渡された時は無視せずエラーにする (統括の推し。黙って無視すると、付け忘れた fd に気づけない)
  - 1 つの値 (pid と fd の番号の組) で受ければ、片方だけの指定が起きない
- CLI は fd を継がなくても、`/proc/<pid>/fd/<N>` を自分で開けばそのディレクトリを掴める (同じ uid)。継いだ fd との照合が要らなくなり、親でないプロセス (同じ uid の daemon 等) の fd も持ち主にできる。未実測

### CLI で選ぶ物

- 綴りが指す物: ソケットのディレクトリ (link-dir。渡した先が名前を足す・rename する・unlink するのに耐える) か、ソケットのファイル (link-file。ファイル名の長さによらない)
- B の綴り: `/proc` を通すか、実パスか
- B の置き場: 自動か、渡されたパスか、渡された fd か
- 用途: bind か connect か (今の resolve の 2 つ)
- 条件を満たせない時に満たさない綴りに落とさずエラーにする形は、`usable_cross_uid` と resolve が既に取っている

### 既に決まっていることとの関係

`_ex` で手法を名指しする口と fork の復活は、次を覆す。

| 決まっていること | 出どころ |
|---|---|
| 経路を利用者が選ぶ・組み合わせる口は作らない (「素人が下手な組み合わせで微妙な使い方をする意味は無い」) | DR-0017 の案 U、SPEC の「公開する操作」(kawaz 2026-11-19) |
| 経路の名前は診断用で、中身を約束しない (契約にすると経路の追加・変更が破壊的変更になる) | DR-0017 の案 V、SPEC の「診断」 |
| fork の経路を作らない。最終手段の引数も無い (副作用がプロセス全体に及ぶ。3 言語で届く所がそろう) | DR-0017 の「fork をしない」と案 J (kawaz 2026-11-20) |

- 分かれ目は「経路の名前を約束に入れるか」。入れれば、除く・足す (fork を含む)・順を変えるを 1 つの並びで表せる。入れなければ、条件ごとの引数を足す形になる
- bind に使ってはいけない手法 (proc-direct・relative・at-direct は綴りが後で無関係なファイルに当たる、widened はアドレスが切れて読む側を壊す) は、名指しされても通さない制限が要る
- fork を作れるのは Rust だけ (Python は難しく、Go と TypeScript は作れない。[fork-cwd](../../pages/fork-cwd-ja.md))
- 利用者 2 つの回答 (2026-11-20) は「fork をやめても困らない。当たるのは seccomp の下でファイル名 80〜96 バイトの時だけ」

## 方向 (kawaz 2026-11-22)

- ライブラリの API (`_ex`) には手法を名指しする口を足さない (足す意義が薄い)。DR-0017 の「経路を選ぶ口は作らない」「経路の名前は診断用」「fork をしない」はライブラリではそのまま
- 手法の名指しは CLI に置く。需要のためでなく、利用者が手法ごとにどんな性質のソケットができるかを自分で試して確かめられるようにするため。アプリに組み込まれない CLI なら、余計な実装が利用者のアプリの容量を増やさない
- 名指しした手法がその環境・その言語で使えない時 (fork を作れない言語、スレッドの cwd を使えないプロセス、`/proc` の無い環境) は、使えない旨のエラーにする
- 既定の試す順 (操作ごとに使ってよい手法と順) は preset として整理する
- CLI の主な客は、短い綴りを作る道具として使う人。`--help` には基本だけを載せる: `resolve` サブコマンド、用途 (bind / connect / sendto 等)、置き場の指定、`sweep` サブコマンド。手法の名指し等は `--help-all` に進んだオプションとして出す

### `resolve` の既定の綴り (kawaz 裁定 2026-11-22)

CLI は綴りを出して終わるので、D の flock を持つプロセスがいなくなる。既定の B (`/tmp/sockat-<uid>`) に D を作ると、他のプロセスの `sweep()` に「使われていない」とみなされて消される。そこで、D を作らない形にする。

- B の直下に、ソケットのディレクトリの realpath のハッシュを名前にした、そのディレクトリを指す E を置いて使い回す ([ハッシュの名前の E の案](2026-11-21-connect-persistent-hashed-e.md) と同じ形)。綴りは `B/<ハッシュ>/<ファイル名>`
- 同じディレクトリにはいつも同じ E が使われ、同じ長いパスにはいつも同じ短いパスが返る。E はディレクトリの数で頭打ちになる
- 出した綴りはそのまま使ってよく、片付けは要らない。`sweep` は B の直下の E に触らない (今の SPEC のまま)。OS の掃除で消えても、次の `resolve` が作り直す
- ディレクトリを指す綴りなので、bind にも connect にも sendto にも同じ綴りを渡せる。用途を選ぶ必要があるのは、ファイル名が長くてこの綴りに収まらず、ソケットのファイルを指す E (link-file) に回る時だけ (connect はどの OS でも使え、bind は macOS と NetBSD だけ)
- 長く動くプログラムに bind 用に渡した後で E が消されると、そのプログラムが終了時に短いパスで unlink しても `ENOENT` で失敗し、ソケットのファイルが残る。E が無い間は connect も届かない。同じパスで `resolve` を呼び直すと直る ([実測](../findings/2026-11-24-cli-base-fd-and-vanished-link.md))。OS の掃除が、使われている E を消すかは確かめていない

## 未決

### 既定以外の綴りの持ち方

- コマンドを包んで起こす形 (`sockat run -- <コマンド>`) を置くか。D の flock の fd を子に継がせれば、子が生きている間は `sweep` に消されず、終われば片付けの対象になる
- 利用者が持つディレクトリの fd と pid を渡す形 (上の「CLI が出した綴りの寿命」) のオプションの名前と値の形

### 手法を試すサブコマンド

- 短い綴りを返せる手法は、ソケットのディレクトリを指す物 (link-dir) とファイルを指す物 (link-file) の 2 つだけ。他 (スレッドの cwd、`/proc` を直接通す、相対パス、広げた sockaddr、`bindat` / `connectat`、fork) は、その場で bind / connect する手法で、綴りを出せない
- 試すには、CLI が実際に bind / connect して、結果 (カーネルが覚えた綴り、綴りの性質、通った手法、置き場に残った物) を表示するサブコマンドが要る。各言語の適合試験用の CLI ([conformance.md](../design/conformance.md)) がしていることに近い
- ライブラリに無い手法 (fork、bind での `/proc` を直接通す綴り・相対パス・広げた sockaddr) は、CLI のためだけに実装と OS ごとの試験が要る。まず今ライブラリにある手法の名指しから作り、無い手法は後から足す案
- CLI が手法を名指しするには、ライブラリに「この手法だけで試す」入口が要る (今は試験がパッケージの中から直接呼ぶ)。公開の API にせず CLI 専用の入口にすれば、ライブラリの約束は増えない

### その他

- 用途の値: 短い綴りの作り方は「その場所にソケットを作る (bind)」と「既にあるソケットに届く (connect)」の 2 種類。sendto は connect と同じ綴り、返信を受ける DGRAM の送り手の bind は bind と同じ綴り
- CLI は Rust で作る (kawaz 2026-11-22。他の言語では作れない経路がある)。置き場所は sockat-rs。CLI の依存をライブラリの利用者に足さないよう、crate の分け方は sockat-rs で決める
- ここまでの決定と統括の案は [DR-0018](../decisions/DR-0018-cli-resolve-with-reused-hashed-link.md) にまとめた
- 片付けの口 (利用者が今すぐ消したい時の `cleanup` に当たるサブコマンド)
