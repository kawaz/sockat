# 利用者向けの文書を 3 段に組み直す (README → 使う上で知ること → 仕組み)

## 概要

- 客は、Unix domain socket のパス長のエラーに困って解決策を探しに来た利用者とアプリ開発者 (kawaz 2026-11-22)
- 今の README は「このリポは何か」と例外の注意から始まり、困っている人に「置き換えるだけで解決する」が伝わらない
- 入口から順に深くなる 3 段にする。上の段ほど技術の詳細を置かない

| 段 | 置き場 | 書くこと |
|---|---|---|
| 1 | README (ハブと各言語) | 見覚えのあるエラー文言 (各言語の標準の実物)<br>置き換えるだけの書き換え前後を各言語で<br>sockat が裏で短い道を用意するので、利用者は考えなくてよいこと<br>言語ごとのパッケージの表<br>2 段目・3 段目への案内 |
| 2 | pages/ の新しいページ | 環境によって一時ディレクトリに小さなディレクトリができること (容量はほぼ 0、大抵は自動で消える、気になる時の掃除の API)<br>stream の他に DGRAM も使えること<br>短い綴りだけを作る API (resolve)<br>短い綴りを作る CLI (できてから載せる。[CLI の issue](2026-11-22-cli-and-route-selection.md))<br>各言語で同じに使えるライブラリがあること |
| 3 | pages/ の新しいページ | sockat がどう短い綴りを作るか。検討した手法、手法ごとの適用範囲と長所・短所の比較、集約した API がどれを選ぶか。届く範囲の表・fork-cwd・SPEC-routes・DR へつなぐ |

- README の末尾の案内は「もっと詳しく」の下に、利用マニュアル (`pages/manual`、2 段目)・リファレンス (`pages/reference`)・技術説明 (`pages/technical`、3 段目) の 3 つの名前だけを並べる (kawaz 2026-11-22)
- リファレンスは各言語の API リファレンスのこと。ハブの利用マニュアルとリファレンスは、どんな API があるかの大まかな説明と、各言語のマニュアル・API リファレンスへの入口にする。各言語のリポの README も同じ構成にし、利用マニュアルとリファレンスはその言語の物へ、技術説明はハブへ張る (kawaz 2026-11-22)
- 各言語の今の文書の持ち方: Rust は MANUAL と docs.rs、Python は MANUAL (API リファレンスを兼ねる)、Go は README (全部入り) と pkg.go.dev、TypeScript は README (全部入り)。Go と TypeScript は README を軽くするなら、マニュアルを分ける必要がある
- ハブの入口で言語を選んで、その言語のマニュアルやリファレンスへ直接飛べる形が望ましい (kawaz 2026-11-22)。md では、ハブの利用マニュアルとリファレンスの先頭に言語の表を置く。GitHub Pages にする時はセレクタにする
- README は軽く保つ (kawaz 2026-11-22): 置き換えの例は 1 言語だけにし、他の言語は各言語のリポの冒頭に載せて、そこへ飛ばす。入れ方も各言語のリポに置く (全言語の入れ方を並べる意味は無い)。この段で読者が知りたくない話題の箇条書き (「もっと知る」の類) を置かず、先への案内は 1 文にする。対応する言語が増えても 1 言語が 1 行以上の場所を取らない形にする
- 2 段目も、言語ごとの名前の表を並べず、1 つの言語の名前で書いて各言語のリポへ飛ばす
- 1 段目と 2 段目は「使う前に知っておくこと」「注意」の枠で書かない (それがあるだけで使いたくなくなる。kawaz 2026-11-22)。2 段目は「他にできること」(DGRAM、短いパスだけを作る、片付けまで任せる) と、裏で作られる物を気にしなくてよい理由で書く。まれな場合の注意 (ファイル名がとても長い時のアドレス等) は仕様と各言語のマニュアルに置く
- 検索から入るランディングページ (エラー文言や関数名を並べ、README へ案内する) は、pages/ の公開の経路ができてから。GitHub Pages のトップにするなら、言語をタブかセレクタで選んで、その場でその言語の例を見られる形にする (kawaz 2026-11-22)
- 各言語のリポの README も、1 段目はその言語の例で持つ。「言語によらない説明は写さずハブへリンクする」は 2 段目以降に限る (kawaz 2026-11-22)
- JavaScript / TypeScript は、ランタイムによらない形で書く (kawaz 2026-11-22)。標準に長いパスを渡した結果は Node.js と Bun、同梱の libuv の版で違う (通る、`EINVAL`、黙って切り詰める。[実測](../findings/2026-11-22-std-errors-on-long-path.md)、[TypeScript 版の調査](../research/2026-11-21-typescript-port.md))。例は Node.js と Bun の両方で動く `node:net` の形 (`bind` / `connect`) を使い、売りは「どのランタイムでも同じに動く」にする

## 受け入れ条件

- [x] 各言語の標準が長いパスで出すエラー文言を実機で採る (macOS と Linux。[findings](../findings/2026-11-22-std-errors-on-long-path.md))
- [x] ハブの README (日英) を 1 段目の形にする
- [x] 2 段目のページ (利用マニュアル `pages/manual`、日英) を書く
- [x] 3 段目のページ (技術説明 `pages/technical`、日英) を書く
- [x] AGENTS.md と SPEC の「各実装に求めること」の、各言語の README に関する決まりを直す
- [x] ハブのリファレンスのページ (`pages/reference`、日英) を書く
- [x] 各言語のリポの README を 1 段目の形にし、末尾に利用マニュアル・リファレンス (その言語の物)・技術説明 (ハブ) の 3 つを置く (Python と TypeScript は push 済み、Go は v0.4.5 で公開、Rust は手元に commit 済みで次の版と一緒に出す)
- [x] 利用マニュアルを「使い方」の形に組み直す (kawaz 2026-11-22。今の「できること」の紹介は、利用者の知りたいことでない)
  - 利用者は、何に使いたいかを知って来る。bind か connect が 9 割、次にパスだけを解決したい人 (resolve)、その後に DGRAM 等
  - マニュアルのトップは、その並びだけにする
  - その先は、トピックごとのページ。bind・connect 等それぞれの利用の場面ごとに、典型的なサンプルコードを見せる
  - ハブの利用マニュアルは、各言語へのリンクを並べてそちらへ誘導する。概要は置いてよい。各言語版と同じ構成で、言語によらない概念の説明として書いておくのもあり (kawaz 2026-11-22)
  - 各言語のマニュアルの形 (統括。ハブから安定して張れるよう、4 言語でパスをそろえる):
    - `docs/MANUAL-ja.md`・`docs/MANUAL.md`: トップ。したいことの並びだけ。順は bind、connect、DGRAM、SEQPACKET、resolve (kawaz 2026-11-22)
    - `docs/manual/bind-ja.md`・`connect-ja.md`・`datagram-ja.md`・`seqpacket-ja.md`・`resolve-ja.md` (と英語の `.md`): 場面ごとの見出しと、典型的なサンプルコード。説明は要る時だけ 1 文
    - SEQPACKET のページは、「resolve で作ったパスを使えばよい」という短い案内と、resolve のページへのリンクだけにする。直接のラッパーになる API は無くてよい。マニュアルで案内すれば利用者は困らない (kawaz 2026-11-22。TypeScript は標準に無いので対象外)
    - `docs/REFERENCE-ja.md`・`docs/REFERENCE.md`: 使い方でない物 (関数と型の一覧、`Options`、`Spelling`、エラー、使ってはいけない書き方、その言語に固有の注意、OS × 経路の表、仕様へのリンク)。API の文書が別にある言語 (docs.rs、pkg.go.dev) は、先頭でそこへ張る
  - ハブのトップは、各言語がそろったら「したいこと × 言語」の表にする。それまでは言語の表だけにする (「できること」の紹介は消した)
- [x] リファレンスに CLI のことも載せる。CLI の利用マニュアルはハブに置き、そこへ張る (kawaz 2026-11-22。CLI を公開する時に)
- [ ] 技術説明の構成と分け方は、後で考える (テーマごとに分けても量がある。worker に任せてよい。kawaz 2026-11-22)
- [ ] Q&A (`pages/faq`) は、ネタを溜めるメモとして今のまま置く (kawaz 2026-11-22。構成を考える時に直す)。載せる予定のネタ: CLI の「通したのに短くならない・長くなった」([DR-0018](../decisions/DR-0018-cli-resolve-with-reused-hashed-link.md))
- [x] CLI の公開 (ライブラリ 0.6.0 と sockat-cli 0.1.0 を同じ release で出す) の前に、ハブに CLI の利用マニュアルを書く (書いた。公開まで README 等からは張らない。公開の時に、実物の出力と合っているかを見直す): `pages/cli-ja.md` と `pages/cli.md`。CLI の `--help` の末尾が `pages/cli.md#environment` を指しているので、環境変数の節の見出しは英語が `Environment`、日本語が「環境変数」

- [x] README の「短いパスは今までどおり…そのまま渡します」は、DR-0019 の後も言い直さない (kawaz 2026-11-22、RM-Q1 = b。「そのまま」を外すと意味が変わる)
