# 3 つのモデルに出したレビューと文書の書き直しを読んで、どう直すかを決める

## 概要

- kawaz の指示 (2026-11-25): 日本語と言葉の扱いが丁寧そうな Gemini に、プロジェクトをレビューさせ、文書を書き直させてみる。比べるために別のモデルにも同じ事をさせる
- 出した結果を読んで、どれを採るか、どれも採らずにこう直すか、を決める (次のセッションで kawaz と)
- 仕様を絞る話 ([issue](2026-11-24-trim-spec-to-what-is-used.md)) と、「手法」と「ルート」の語を直す話は、この結果を見てから進める

## やった事

道具は `agy -p` (Antigravity の CLI)。3 つのモデルに、同じ文面の 4 つの依頼を順に流した。

| 依頼 | 中身 | 出力 |
|---|---|---|
| 1 | プロジェクト全体のレビューと評価 | `1-review.md` |
| 2 | 文章の良くない点・日本語の変な点・分かりにくい点を全部洗い出し、直すならこう、を書く | `2-writing.md` |
| 3 | 「手法」と「ルート」の区別 (kawaz の言葉のとおりに書いて渡した) を理解させた上で、直す所を全部出す | `3-terms.md` |
| 4 | 自分の 3 つの報告を読んだ上で、別のディレクトリに、ハブの文書を自由に書き直す | `rebuild/` (`REBUILD-NOTES.md` に方針と、今の構成との対応表) |

- 入力: ハブ (`744990a`) と 4 言語のリポの、その時点の中身の写し (書き込み禁止)
- 置き場: リポの `artifacts` の workspace の `model-review-20261125/` (版管理はしていない)。モデルごとに `carbon/`・`neon/`・`opus/`。依頼の文面は `prompts/`、流し方は `run.sh`、進みは各モデルの `progress.log`
- ブラウザ: `https://artifacts-kawaz-sockat.<host>.tmpspace.net/model-review-20261125/` (tailnet の中だけ)

## 読み比べ (2026-11-25)

依頼ごとに worker (Opus high) が全部を読み、入力の写しを開いて裏取りした。全文は `model-review-20261125/compare/` の `1-review-compare.md`・`2-writing-compare.md`・`3-terms-compare.md`・`4-rebuild-compare.md`。実機では動かしていない (読んで確かめただけ)。

前提: モデルに渡した写しは `744990a` の時点の物で、[仕様を絞る issue](2026-11-24-trim-spec-to-what-is-used.md) の「kawaz の考え」の節が入っていない。「手法」と「ルート」の区別だけは、依頼 3 の文面で渡した。依頼 1 のレビューと依頼 4 の書き直しは、「したい事を先に受け取る」「条件の組」を知らずに書かれている。

モデルごとの性格:

- Carbon: 大きく組み替えて縮める。構成の案と、語の型の箇所の一覧 (307 か所、全部正しい) が使える。直した文は長くなり、造語 (「中継ディレクトリ」等) と注意書きが増える。書き直しは、断りなく規定を落とし (`sweep_base`、`Options.base` の格下げ)、黙って symlink の時刻を新しくする作りを入れている
- Neon: 正確で網羅が厚い。実装の中まで降りた食い違いの指摘と、語を直す箇所の台帳 (各言語のリポまで) が使える。書き直しは量が減らず、造語「実渡パス」を 113 回使い、README は今より重い
- Opus: 文章の直しがそのまま使える率が最も高く、文を分ける向きで直す。語の定義の言い直しが最も忠実で、定義だけでは決まらない所の問いを 14 件挙げた。依頼 1・4 は無く、依頼 3 は途中

3 つとも使えない物:

- 「置き場」「綴り」の言い換えの案 (どれも別の造語に置き換えている)
- 依頼 2 の中の「経路」と「手法」の整理 (個々の技を「経路」に揃える向きで、区別と逆)
- `usable_cross_uid` を削る提案 (Carbon・Neon)。別の uid から辿れるかは、kawaz の考えでは先に受け取る条件の例

語の区別で、モデルの分類が割れた所 (定義だけでは決まらない所の候補):

- 診断の `route` の値は手法の名前で、パスではない。届く範囲の表の「通った経路」の列を、Carbon は「ルート」、Neon は「手法」とした
- 失敗した時の `route` は、結果のルートに当たらない
- 「ルート」1 語に 3 つの役を持たせるか (Carbon・Neon)、並べた順だけに当てるか (Opus)
- カタカナの「ルート」が、ファイルシステムの根 `/` と重なる (今のハブの文書の「ルート」5 回は全部こちら)
- 環境 (OS、`/proc` の有無) の違いは別のルートか、1 本のルートの中で使えない手法を飛ばすだけか
- 絶対パスの候補作り・procB と実パスの違いを、手法と数えるか

3 モデルで揃った案: 個々の技の英語は technique、`SPEC-routes-ja.md` は `SPEC-techniques-ja.md`、`--route` と `skipped` は名前を残す、SPEC の節を「手法」と「ルート」に分ける。

## 使い方で分かった事 (`agy -p`)

- 読んで答えるだけなら、そのまま動く
- シェルのコマンドを使おうとすると、対話なしでは権限を聞けず、何も返さずに終わる (`a tool required the "command" permission`)。依頼に「シェルを使わず、ファイルを読む・書く道具だけ使う」と書くと通る事が多いが、守られない事もある (Opus の依頼 1)
- 別のディレクトリに書かせるには、`--add-dir <出力先>` と `--mode accept-edits` を付ける
- モデルの名前は `agy models` で見られる
