## 裁定待ち

### HB-Q1 fork の経路を作れない言語で `connect_any` 系を公開するか

Go のように fork を安全に作れない言語では、`connect_any` は `connect` と同じ経路しか試せない。関係: [SPEC-ja](SPEC-ja.md) の「未確定」

- [ ] a: 公開しない (統括推し。中身が `connect` と同じ関数は、呼ぶ側に「fork でやり切る」と誤解させる。README の表に「fork の経路なし」と書く)
- [ ] b: 公開し、fork が要る場面では `connect` と同じエラーを返す (言語をまたいで関数の並びが揃う)

### HB-Q2 標準のソケットが非同期を前提とする言語 (Node.js 等) で、`connect` と `connect_nonblocking` をどう対応させるか

Node.js の connect は元から待たない (コールバック / Promise で結果を返す)。ブロックする connect が無い。

- [ ] a: その言語の標準の connect と同じ形 (非同期) を 1 つだけ出し、`_nonblocking` の区別を持たない (統括推し。標準と同じ形で使えることが sockat の約束)
- [ ] b: Rust と同じ名前の 2 つを揃える

### HB-Q3 標準の上限が `sun_path` − 1 より短い言語で、その差の長さのパスをどう扱うか

Java の標準は `sun_path` − 2 までしか受け付けない。SPEC の「`sun_path` − 1 まで標準にそのまま渡す」をそのまま当てると、その 1 バイトの長さのパスを標準が断る。

- [ ] a: 「その言語の標準が受け付ける長さまで標準に渡し、それを超えたら経路に回す」と SPEC を言語に依らない形で書き直す (統括推し。「標準が通すものは標準と完全に同じ」という約束がどの言語でも保てる)
- [ ] b: `sun_path` − 1 のまま、その言語だけ例外として書く
