# DR-0019: bind と resolve は、相対パスを cwd で絶対パスにしてから扱う

- Status: Active (未実装。問いは全部裁定済み。4 言語に実装を頼み、それぞれ次の minor の版で出す)
- Date: 2026-11-22

## Context

- 相対パスで bind すると、カーネルが覚える綴りは相対のままになる。後で cwd が変わると、その綴りは別の所を指す (`Spelling` の `CwdRelative`)
- 相対の綴りで起きる事故

| 場面 | 起きること |
|---|---|
| listener を閉じる時にアドレスの綴りで unlink する標準 (Go の `UnixListener.Close`) | bind の後で cwd を変えていると、ソケットのファイルが消えないか、別の場所の同じ名前のファイルを消す |
| 閉じた時点の cwd で、渡されたパスを unlink する標準 (Node・Bun) | 同じ |
| DGRAM の受け手が、送り手のアドレスへ返信する | 受け手の cwd が違うと届かない ([実測](../findings/2026-11-22-dgram-reply-to-relative-sender.md)) |
| 深い cwd で、絶対パスなら長すぎるので相対パスで bind する (よくある回避策) | 上の全部に当たる |

- [DR-0017](DR-0017-resolve-through-persistent-base.md) は、相対パスを入口で絶対パスにする案 (案 AC) を「短い相対パスが標準と違う経路に回り振る舞いが変わる」として採らなかった。その時の設計は bind のたびに乱数の名前を挟んですぐ片付ける形で、絶対にすると手数と片付けが増えた
- 今の設計は、綴りを残して使い回す (既定の bind の link-dir の E は、ディレクトリごとに 1 つ)。絶対にしても増える物が少なく、上の事故を未然に防ぐ意味が加わる (kawaz 2026-11-22)
- CLI の `resolve` は、相対パスを絶対にしてから長さで分けると決めてある ([DR-0018](DR-0018-cli-resolve-with-reused-hashed-link.md))

## Decision

### 絶対パスにする操作

| 操作 | 相対パスを受け取ったら |
|---|---|
| bind 系 (`bind`・`bind_ex`・`datagram::bind`・`datagram::bind_ex`) | 絶対パスにしてから扱う |
| resolve (`resolve_for_bind`・`resolve_for_connect`) | 絶対パスにしてから扱う (返した綴りは、後で cwd が変わった後にも使われうる) |
| connect 系 (`connect`・`connect_nonblocking`・`datagram::connect` と各 `_ex`) と、送信の宛先 (`datagram::send_to`) | 変えない (綴りは相手に残らず、つないだ・送った後は cwd の変化も関係ない。相対のまま渡せば置き場に何も作らない) |

### 絶対パスの作り方と、その後

1. 引数の形の検査 (空のパス、NUL、`Options.base` の形) は今のとおり先に行う。abstract の名前は対象外
2. 相対パスなら、同じ所を指す絶対パスの候補を 2 つ作る (kawaz 2026-11-22)

| 候補 | 作り方 | 確かめ |
|---|---|---|
| 実パス | ソケットのディレクトリを realpath で実パスにし (symlink を辿る)、ファイル名を付ける | realpath が OS に引かせた結果なので要らない |
| `$PWD` からの綴り | `$PWD` (`stat` の `(st_dev, st_ino)` が `.` と一致する時だけ使う) に相対パスを文字列でつなぎ、`..` と `.` を字句で畳む | 畳んでできたディレクトリの `(st_dev, st_ino)` が、元の相対パスのディレクトリと同じ時だけ候補にする (`a/sym/..` は字句で畳むと別のディレクトリになりうるため) |

3. 候補のうち、標準に渡す長さ以下の物があれば、それを標準に渡す (実パスを先に見る)。綴りは絶対パスで、`Spelling` は `Original`。置き場には何も作らない。標準に渡す長さを超える絶対パスを受け取った時も、経路に進む前に実パスの候補を試し、収まればそれを標準に渡す
4. どちらも収まらないか作れなければ、長いパスの経路に進む (今の長い相対パスと同じ。sockat の作る綴りで、`Linked` 等)
5. 4 でどの経路も使えない時は、元の相対パスを今と同じに扱う: 標準に渡す長さ以下なら相対のまま標準に渡し (`Spelling` は `CwdRelative`)、超えるなら今の長い相対パスの経路に進む。標準で届く所に届かなくならないようにする

- 候補を 2 つ見るのは、標準にそのまま渡せる場面を増やすため (実パスの方が短い時も、`$PWD` の綴りの方が短い時もある)。収まれば置き場に何も作らずに済む。短さは競わない (収まっていれば足りる)
- 5 に落ちるのは、経路自体が使えない時だけ。絶対にした形で実際に bind して失敗した時 (`EADDRINUSE`・`ENOENT` 等) は、そのエラーを返し、他の候補や相対パスで試し直さない (同じ失敗を 2 回試したり、別の所に作ったりしないため)
- cwd がとても深い (絶対パスが PATH_MAX を超える。Linux 4096、macOS 1024) と、realpath も `$PWD` の綴りも作れないか収まらない。そういう利用者は 4 か 5 に進む
- 候補の作り方は、connect の relative の「[相対パスの作り方](../SPEC-routes-ja.md#相対パスの作り方)」(cwd の綴りを削る形と実パスから作る形を作り、`(st_dev, st_ino)` で確かめる) と同じ考え方の逆向き
- `/proc/self/cwd/…` のような、絶対パスだが cwd に依る綴りには触らない (相対パスだけが対象)
- `CwdRelative` が返るのは 5 の場面だけになる
- 相対パスの `remove()` のための cwd の見張り (呼び出しの前後で cwd の `(st_dev, st_ino)` を比べる) と、標準がパスとして読まない綴りに `./` を付ける扱い (Node の数値に読める文字列、Go の illumos の `@`) が要るのも、5 の場面だけになる

理由:

- 既定の `bind` の利用者は `Spelling` を見ないので、`CwdRelative` で知らせても事故に気づけない。絶対にすれば、利用者が何もしなくても起きない
- 変わるのは「カーネルが覚える綴りが相対か絶対か」で、ソケットのファイルができる場所は変わらない
- 5 で相対のまま渡す道を残すので、標準より届かなくなる場面ができない

悪い面:

- 短い相対パスで、カーネルが返すアドレス (`getsockname`、相手の `getpeername`、`ss`・`lsof` 等) が相対でなく絶対になる (標準と違う)。アドレスの文字列を、渡した相対パスと比べるコードは合わなくなる
- 深い cwd で短い相対パスを bind すると、標準なら何も作らずに済んだ所で、置き場に B・D・E ができる。「短いパスは標準にそのまま渡す」が、相対パスには当たらなくなる
- 相対パスの bind のたびに、realpath と `stat` の手数が増える (bind は息が長く大量には行わない操作で、速さより残る綴りの安全を重視する)
- 候補を作ってから bind するまでの間に cwd が変わると、候補を作った時点の cwd の場所に作る (標準の相対パスの bind は bind の時点の cwd)
- 4 言語の実装と適合試験を直し、0.x の minor を上げる (振る舞いが変わる)。`CwdRelative` と `remove()` の相対パスの試験の多くを書き直す

## Alternatives Considered

- 案 A: 今のまま、`CwdRelative` で知らせるだけにする
  - 不採用理由: 知らせを見るのは `_ex` と resolve を使う人だけ。消すのは利用者のコードでなく上のライブラリのことが多く、利用者が避けにくい
- 案 B: connect 系も絶対にする
  - 不採用理由: connect の綴りは相手に残らないので意味が無く、手数だけ増える
- 案 C: 絶対にした形で届かない時はエラーにする
  - 不採用理由: 標準なら届く短い相対パスが、sockat に置き換えると届かなくなる
- 案 D: cwd を前に付けるだけにし、`..` を畳まず、realpath も使わない (候補を 1 つにする)
  - 不採用理由: 畳まない綴りは `../` の分だけ長く、標準に収まる場面が減る。実パスの方が短い環境 (symlink を通した長い作業ディレクトリ) も拾えない。収まらないと置き場に物を作ることになる
- 案 E: `..` を字句で畳み、確かめずに使う
  - 不採用理由: `a/sym/..` はカーネルでは symlink の先の親を指す。字句で畳むと別のディレクトリになる

## Consequences

- 裁定が揃ったら、この DR と SPEC・DR-0017・DR-0018・各言語の実装との整合を通しで確かめ直す (綴りの性質を返す所と返さない所の整理を含む。kawaz 2026-11-22)

- SPEC (短いパス、bind の順、`Spelling`、`remove`、長いパスで標準と違う点、使ってはいけない書き方、試験の観点) と DR-0017 の案 AC の記述、届く範囲の表を直す
- 各言語の実装と適合試験の場面を直す
- README と各言語の README の「短いパスは今までどおり標準にそのまま渡す」の言い方を見直す

## 裁定

- kawaz (2026-11-22、RL-Q2 = a): 4 言語に実装を頼み、それぞれ次の minor の版で出す (Rust は 0.6.0)
- kawaz (2026-11-22): 相対パスを絶対にする方向に変える
- kawaz (2026-11-22): 絶対パスの候補は実パスと `$PWD` からの綴りの 2 つ。`../` を畳んだ綴りは元と同じ所を指すと確かめてから候補にする。収まればそれを使い、収まらなければ sockat の作る綴りに進む
- kawaz (2026-11-22、RP-Q2 = a): connect のように、つないだ後に相手のことや cwd の変化を気にしなくてよい操作は、置き場に何も作らない相対パスのまま使う。絶対にするのは bind 系と resolve だけ。送信の宛先 (`send_to`) も connect と同じ扱い
- kawaz (2026-11-22、RP-Q4 = a): `resolve_for_connect` が返す `ForConnect` にも綴りの性質 (`Spelling`) を持たせる。connect で性質を返さないのは、resolve の直後に使うと決まっているから。resolve した綴りは長く持って使うことがありうるので、相対のままであること (cwd が変わると使えない) や、`/proc` を通す綴りの寿命 (そのプロセスの間だけ) を構造体で返す
- kawaz (2026-11-22、RP-Q1 = a): 5 の、どの形でも届かない時は、相対のまま標準に渡す
- kawaz (2026-11-22、RP-Q3 = a): 長い絶対パスの bind と resolve でも、経路に進む前に実パスの候補 (ソケットのディレクトリの realpath + ファイル名) を試し、収まればそれを標準に渡す (CLI の `resolve` と同じ)
- 統括が決めた細部: 候補は実パスを先に見る
