# DR-0018: 短い綴りを作る CLI を Rust で作る。既定の `resolve` はディレクトリを指すハッシュの名前の E を使い回し、手法の名指しは CLI だけに置く

- Status: Active (部分実装: `resolve`・`sweep`・補完を sockat-rs 0.6.2 で公開。入れ方は Homebrew `kawaz/tap/sockat`、crates.io の sockat-cli、GitHub Release の実行ファイル。手法の名指しと手法を試すサブコマンドは未着手)
- Date: 2026-11-22

## Context

- sockat を組み込めないプログラム (他人の作ったコマンド) に、長いパスの代わりに短い綴りを渡したい利用者がいる。ライブラリでは届かない客
- アプリに組み込む前に、sockat がどんな綴りを作るかを手元で試したい利用者がいる (kawaz 2026-11-22)
- CLI は綴りを出して終わる。ライブラリの綴りの作り方をそのまま使うと、次が起きる
  - D の flock を持つプロセスがいなくなり、他のプロセスの `sweep()` と OS の掃除に「使われていない」とみなされて消される
  - `/proc/<pid>/fd/<fd>/…` の綴り (procB) は、CLI が終わった時に辿れなくなる
- 手法ごとにどんな性質のソケットができるかを、利用者が自分で試して確かめられる口が欲しい (kawaz 2026-11-22)。ライブラリの API に手法を名指しする口を足す意義は薄い。アプリに組み込まれない CLI なら、余計な実装が利用者のアプリの容量を増やさない
- 持ち主の pid を親の pid から黙って決めると、コマンド置換の中のパイプや複文で、すぐ終わるプロセスを持ち主にしてしまう (実測 2026-11-22。[issue](../issue/2026-11-22-cli-and-route-selection.md))

## Decision

### 目的

- CLI の目的は、OS の上限の中で bind / connect がエラーにならない、同じ場所を指す綴りを出すこと。短くすることが目的ではない (URL の短縮の道具とは違う)。出した綴りが一見長くても (macOS の `/private/tmp/…` 等)、上限に収まっていることを約束する (kawaz 2026-11-22)
- だから、綴りを 1 バイトでも短くする工夫 (置き場を実パスでなく `/tmp` で綴る、ハッシュを削る等) はしない。元のパスが収まっていれば、そのまま出す

### 作る物と置き場所

- コマンド `sockat` を Rust で作り、sockat-rs のリポに置く (全部の経路を作っていて、他の言語では作れない経路がある)
- CLI の依存 (引数のパーサ等) をライブラリの利用者に足さない。crate の分け方と名前は sockat-rs の DR で決める
- ハブは、サブコマンド・オプション・出力・既定の綴りの作り方を決める (この DR と、後で書く設計文書)

### サブコマンドと `--help`

| サブコマンド | すること | 載せる所 |
|---|---|---|
| `resolve <パス>` | 短い綴りを標準出力に 1 行で出す | `--help` |
| `sweep` | ライブラリの `sweep()` と同じ (置き場 1〜3 の死んだ D を消す) | `--help` |
| `bind <パス>`・`connect <パス>` | 手法を名指しして実際に bind / connect し、結果を表示する (手法を試す用) | `--help-all` |

- 主な客は、短い綴りを作る道具として使う人。`--help` には `resolve`・`sweep` と、置き場の指定等の基本のオプションだけを載せる。手法の名指し等は `--help-all` に進んだオプションとして出す
- `sockat <パス>` は `sockat resolve <パス>` の省略形にする (主な使い方を一番短く書けるように)。最初の引数がサブコマンドの名前ならサブコマンドとして扱う
- `resolve` は `--json` で、綴りと一緒に長さや作り方を JSON で出す
- 引数なしは `--help` を表示する。オプションはロングオプションを基本にする。補完の定義を出す口を持つ
- 呼び方・オプション・出力・終了コードの決まりは [docs/design/cli.md](../design/cli.md)

### `resolve` の既定の綴り

D を作らず、B の直下に、ソケットのディレクトリを指す E を置いて使い回す。

1. パスが sockaddr に入る長さ以下なら、そのまま出す (渡す先のプログラムの言語は分からないので、言語ごとの「標準ライブラリに渡す長さ」でなく sockaddr に入る長さで分ける)
2. ソケットのディレクトリを引く (無ければ `ENOENT`、ディレクトリでなければ `ENOTDIR`)
3. B を選ぶ。作り方と確かめはライブラリと同じ ([SPEC-routes の「B の作り方」](../SPEC-routes-ja.md#b-の作り方))。置き場は `/tmp` → `$XDG_RUNTIME_DIR` → `$TMPDIR`。ソケットのディレクトリには作らない (B の実パスの綴りが元のパスより長くなる)
4. B の直下の E の名前は、ソケットのディレクトリの realpath のバイト列の SHA-256 の 16 進小文字の先頭 12 文字。無ければ作る。あれば `readlink` で指す先を確かめ、同じならそのまま使い、違えば乱数の名前で作って rename で置き換える
5. 綴り `B/<ハッシュ>/<ファイル名>` が sockaddr に収まれば、それを出す
6. 収まらない時 (ファイル名が長い) は、ソケットのファイルを指す E (名前はそのファイルの綴りのハッシュ) を同じく B の直下に置き、綴り `B/<ハッシュ>` を出す。この綴りは connect にはどの OS でも使えるが、bind に使えるのは bind が symlink を辿る OS (macOS・NetBSD) だけ。用途の指定が無ければ connect 用として出し、どの OS でも「bind には勧めない」の警告を理由つきで標準エラーに出す (`--json` の時は JSON の中に入れる)。理由は、bind が symlink を辿らない OS では bind が失敗すること、辿る OS でもこの綴りで unlink するとソケットのファイルが残ること。`--for bind` を指定して、その OS で bind に使える綴りを作れない時はエラー (kawaz 裁定 2026-11-22、CL-Q1 = b)
7. どれも作れない・収まらない時は `ENAMETOOLONG` のエラー

- 5 の綴りはソケットのディレクトリを指すので、bind にも connect にも sendto にも同じ綴りを渡せる。用途の指定が効くのは 6 だけ
- 同じディレクトリにはいつも同じ E が使われ、同じ長いパスにはいつも同じ短いパスが返る。E はディレクトリの数で頭打ちになる
- 出した綴りはそのまま使ってよく、片付けは要らない。`sweep` は B の直下の E に触らない ([SPEC の `sweep`](../SPEC-ja.md#sweep) のまま)。OS の掃除で消えても、次の `resolve` が作り直す
- 標準出力には綴りだけを出す。失敗は標準エラーに原因と対処を出し、終了コードを 0 以外にする。満たせない時に、満たさない綴りを黙って出さない

### 置き場と持ち主の指定

| オプション | 中身 |
|---|---|
| 置き場の指定 | B そのもののパスを渡す (ライブラリの `Options.base` と同じ確かめ) |
| 持ち主の fd と pid | 利用者が開いたディレクトリの fd の番号と、それを持つプロセスの pid を渡す。`/proc/<pid>/fd/<fd>` を B の綴りにし、そのプロセスが fd を持つ間だけ辿れる綴りを出す (Linux で `/proc` を使え、同じ uid・同じ PID 名前空間の相手だけ)。CLI は別のプロセスなので `/proc/<pid>/fd/<fd>` を自分で開く。同じ uid なら開けて、その下に symlink を作れ、綴りに bind・connect・unlink が届く。別の uid は開けない。持ち主が終わると辿れなくなる ([実測](../findings/2026-11-24-cli-base-fd-and-vanished-link.md)) |

- pid は黙って親の pid にせず、引数で受ける。fd 無しで pid だけ渡された時は、無視せずエラーにする (付け忘れた fd に気づけるように)

### 手法の名指し (`--help-all`)

- 手法の名前を並べて渡すと、その順に試す。名指しした手法がその環境で使えない時 (スレッドの cwd を使えないプロセス、`/proc` の無い環境等) は、使えない理由つきのエラーにする
- 既定の試す順 (操作ごとに使ってよい手法と順。SPEC の [bind の順](../SPEC-ja.md#bind-の順)・[connect の順](../SPEC-ja.md#connect-の順)・resolve の 2 つ) は、名前の付いた preset として選べる
- 短い綴りを返せる手法は link-dir と link-file だけ。他の手法はその場で bind / connect するので、`bind`・`connect` のサブコマンドで試す。結果として、カーネルが覚えた綴り、綴りの性質 (`Spelling`)、通った手法、飛ばした手法と理由、置き場に残った物を表示する
- 進んだオプションの名前・手法の名前・表示の形は試す用で、約束しない (経路は増えたり変わったりする)
- まず、今ライブラリにある手法の名指しを作る。ライブラリに無い手法 (fork、bind での `/proc` を直接通す綴り・相対パス・広げた sockaddr) は、CLI のためだけの実装と OS ごとの試験が要るので、後から足す
- ライブラリの「この手法だけで試す」入口は CLI 専用にし、公開の API にしない

### ライブラリは変えない

- ライブラリの API (`_ex`) には手法を名指しする口を足さない。[DR-0017](DR-0017-resolve-through-persistent-base.md) の「経路を選ぶ口は作らない」「経路の名前は診断用」「fork をしない」はそのまま

理由:

- D を作らなければ、flock を持つプロセスがいないことが問題にならない。E の名前を指す先で決めれば、呼ぶたびに増えず、消えても作り直せる
- ディレクトリを指す綴りを先にすれば、渡した先のプログラムが名前を足す・rename する・unlink するのに耐え、用途を聞かずに済む
- 手法の名指しを CLI の進んだオプションに閉じれば、ライブラリの約束が増えず、利用者は全部の手法を自分で試せる

悪い面:

- 長く動くプログラムに bind 用に渡した後で E が消されると、そのプログラムが終了時に短いパスで unlink しても `ENOENT` で失敗し、ソケットのファイルが残る。E が無い間は、その綴りへの connect も `ENOENT`。同じパスで `resolve` を呼び直すと同じ綴りで E が作り直され、connect も unlink も通る ([実測](../findings/2026-11-24-cli-base-fd-and-vanished-link.md)、Linux と macOS。E は手で消した)
- 綴りは `/tmp` を通るので、自分か相手が `/tmp` を隔離している (systemd の `PrivateTmp` 等) と辿れない。その時は置き場か、持ち主の fd と pid を指定する
- E は使われなくなっても残る (macOS の `/tmp` は再起動まで)。数はディレクトリの数で頭打ち
- ハッシュの 12 文字と B の名前の分、届くファイル名が縮む (uid 4 桁で Linux はおよそ 77 バイト、macOS はおよそ 66 バイト。超えると 6 に回る)
- 手法を試す口のために、ライブラリに CLI 専用の入口が増える

## Alternatives Considered

- 案 A: ライブラリと同じく、呼び出しごとに D を作る
  - 不採用理由: CLI が終わると flock を持つプロセスがいなくなり、他のプロセスの `sweep()` と OS の掃除に消される
- 案 B: CLI 専用の置き場に呼び出しごとの E を作り、片付けのサブコマンドを置く
  - 不採用理由: 利用者に片付けを求め、呼ぶたびに溜まる
- 案 C: コマンドを包んで起こす形 (`sockat run -- <コマンド>`) を既定にする
  - 不採用理由: 主な使い方は綴りだけを受け取ること。包む形は後から足せる ([issue](../issue/2026-11-22-cli-and-route-selection.md) の未決)
- 案 D: 用途 (bind / connect) をいつも指定させる
  - 不採用理由: ディレクトリを指す綴りはどの用途にも使えるので、聞く必要が無い
- 案 H: ファイル名が長く用途の指定も無い時は、エラーにして指定を求める
  - 不採用理由: 主な客は引数を増やしたくない。connect 用に出して警告すれば、connect に使う人は何もせずに済み、bind に使う人は警告で気づける (kawaz)
- 案 E: 持ち主の pid を親の pid から決める
  - 不採用理由: コマンド置換の中のパイプや複文で、すぐ終わるプロセスが親になる (実測)。照合はその時点で同じディレクトリかしか見られず、見分けられない
- 案 F: 手法を名指しする口をライブラリの `_ex` にも置く
  - 不採用理由: 足す意義が薄い (kawaz)。経路の名前が約束になり、経路の追加・変更が破壊的変更になる (DR-0017 の案 U・V)
- 案 G: CLI を他の言語で作る
  - 不採用理由: 作れない経路がある (kawaz)

## Consequences

- CLI のサブコマンド・オプション・出力の決まりは [docs/design/cli.md](../design/cli.md)。sockat-rs のセッションに実装を頼む
- CLI を公開したら、Q&A に「通したのに短くならない・長くなった」への答えを置く (kawaz 2026-11-22): sockat は短くする道具でなく、上限に収まるパスを出す道具。収まっているパスはそのまま出す。相対パスは、どこから使っても同じ場所を指すよう絶対パスにするので長くなる (深い cwd で `./bind.sock` に bind した DGRAM の送り手は、受け手が返信できない。絶対にして上限に収めた綴りなら返信が届く。[実測](../findings/2026-11-22-dgram-reply-to-relative-sender.md))。長いパスは `/private/tmp/sockat-501/…` のように短くは見えない形になるが、必ず上限に収まっている (`--json` の `bytes` と `limit` で確かめられる)
- CLI を公開したら、README に「CLI もあります。アプリに組み込む前のお試しに便利です」の節を、`sockat <パス>` と `sockat --json <パス>` の例つきで足す (kawaz 2026-11-22)
- 利用マニュアル (`pages/manual`) に CLI の節を足すのは、CLI を公開した後
- [ハッシュの名前の E の案](../issue/2026-11-21-connect-persistent-hashed-e.md) のうち、名前の作り方と置き換え方をこの DR が使う。ライブラリの connect に入れるかは、その issue のまま

## 未決

- コマンドを包んで起こす形を置くか
- 持ち主の fd と pid のオプションの名前

## 裁定

- kawaz (2026-11-22): CLI を作る。Rust で作る。手法の名指しは CLI に置きライブラリには足さない。使えない手法はエラー。既定の試す順は preset。`--help` は基本だけで進んだオプションは `--help-all`。`resolve`・`sweep` のサブコマンド。`resolve` の既定はディレクトリを指すハッシュの名前の E の使い回しで、片付け不要。持ち主の fd には pid を組で渡す
- kawaz (2026-11-22): README に CLI の節を置く。例は `sockat <パス>` と `--json`
- kawaz (2026-11-22、RL-Q1 = a): `sockat-cli` を crates.io に公開する
- kawaz (2026-11-22): CL-Q1 = b (ファイル名が長く用途の指定も無い時は connect 用に出し、bind には勧めない旨を警告する)。CL-Q2 = a (手法を試す口は、まず今ライブラリにある手法から)
- 統括が決めた細部: `sockat <パス>` を `resolve` の省略形にする、sockaddr に入る長さで分ける、ハッシュの作り方、ソケットのディレクトリには B を作らない、pid だけ渡された時はエラー、ライブラリに無い手法は後から足す、ライブラリの入口は CLI 専用、crate の分け方は sockat-rs で決める
